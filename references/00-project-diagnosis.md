## 诊断目标

先回答三个内部问题：

1. 用户已经完成到哪里？
2. 当前真正阻止项目继续的是什么？
3. 本轮交付什么产物，用户才能直接进入下一步？
4. 用户完成本轮后有哪些可选择的下一步？

不要把“用户最后提到的现象”自动当作根因。视频中的错误道具可能来自资产卡错误、故事板漏锁、首帧错误、提示词引用混乱或模型负载过高，必须追溯上游。

## 证据优先级

按以下顺序确定事实：

1. 用户本轮明确修订和最新确认。
2. 用户标记为最终版、锁定版的项目文件。
3. 已确认的人物、服装、场景、道具和声线资产。
4. 当前分镜、故事板和提示词。
5. 已生成图片／视频中能观察到的事实。
6. 更早版本和模型自行生成的内容。

发生冲突时采用较高优先级，并在修订记录中说明。不要让旧文件或版式参考覆盖最新剧情资产。

## 阶段识别

根据用户现有材料判断阶段：

| 现有材料 | 当前阶段 | 常见下一步 |
|---|---|---|
| 一句话、题材或模糊灵感 | 灵感 | 故事核心和卖点 |
| 小说、故事或素材 | 改编 | 改编方案与分集 |
| 大纲或分集梗概 | 剧本 | 场景、动作和对白 |
| 完整剧本 | 分镜 | 视听切片和读秒 |
| 分镜表 | 资产／故事板 | 查漏并建立资产 |
| 人物或场景卡 | 故事板 | 图片生成提示词 |
| 故事板图片 | 视频 | Seedance提示词 |
| 视频提示词但无法生成 | 视频故障 | 合规／复杂度／引用诊断 |
| 已生成图片或视频 | 质检 | 根因修复和返修版本 |
| 多段视频 | 后期 | 拼接、声音和成片检查 |

若多个阶段并存，标出最靠后的阶段和需要回溯修复的上游阶段。

## 问题分类

| 问题类型 | 典型现象 | 首要修复层 |
|---|---|---|
| 故事问题 | 动机弱、钩子不足、逻辑断裂 | 大纲／剧本 |
| 对白问题 | 漏台词、台词空泛、人物同声同气 | 剧本／声线 |
| 分镜问题 | 内容拥挤、切镜频繁、动作不完整 | 分镜脚本 |
| 资产问题 | 道具、服装、脸、场景错误 | 资产真源 |
| 空间问题 | 跳轴、瞬移、人物从错误方向出现 | 站位／连续性 |
| 生图问题 | 参考图混用、人物错误、版式错误 | 参考职责／生图提示词 |
| 视频执行问题 | 动作失控、角色重复、生成失败 | 视频提示词／镜头复杂度 |
| 合规问题 | 提示词被拦截 | 最小合规改写 |
| 声音问题 | 漏字、含糊、被BGM遮盖 | 对白时长／收音描述 |
| 后期问题 | 重复帧、节奏碎、声音断裂 | 拼接／剪辑 |

## 执行闭环

每轮按以下步骤执行：

1. **盘点**：读取完整材料，列出已确认、未确认、互相冲突和缺失内容。
2. **定位**：找出主问题、根因和受影响范围。
3. **决策**：选择能最小改动解决问题的方案；涉及剧情方向的多个合理选项时才让用户选择。
4. **执行**：直接修改剧本、分镜、资产、提示词或文档。
5. **回归检查**：检查修改有没有造成新的时长、连续性、资产或声音问题。
6. **二次修正**：修掉自检发现的问题后再交付。
7. **推进**：明确项目现在完成到哪一步、已完成和未完成内容，并给出至少三个明确下一步选项。

不要把未经修正的“问题清单”当作最终交付。

## 波及检查

任何修改都检查上下游：

- 剧情修改：分集、大纲、对白、分镜、资产需求和后续钩子。
- 对白修改：说话人、人物口吻、时长、反应动作、音频和口型。
- 角色／服装修改：资产卡、所有出场分镜、故事板和视频提示词。
- 道具修改：资产卡、尺寸、佩戴点、持物手、接触动作、首尾帧。
- 场景修改：拓扑、站位、轴线、入口出口、背景锚点和运镜。
- 分镜修改：前一段尾帧、当前动作、下一段首帧、声音桥和总时长。
- 合规修改：确认没有误删剧情信息和戏剧张力。

## 完成度判定

按证据把各阶段标记为：

- **已完成**：产物实际存在、约定范围完整，并通过该阶段核心检查。
- **进行中**：已有部分内容，但仍存在缺页、占位、未确认或未修复问题。
- **未开始**：没有对应产物。
- **被阻塞**：存在关键资料缺失、设定冲突、工具失败或必须由用户决定的分支。
- **需返工**：虽然已有产物，但错误会阻止后续生产，不能算作已完成。

必须告诉用户：

1. 已经完成了哪些具体交付物。
2. 哪些交付物仍未完成。
3. 哪些看似完成但需要返工。
4. 当前最影响进度的阻塞项。
5. 下一里程碑的完成标准。

只有项目总范围已知时才计算百分比。计算方式优先使用“已通过的交付物数量／计划交付物总数”或“已通过的阶段权重／总阶段权重”，并写清依据。不要仅凭聊天轮数估算。

## 下一步选择

每次进度分析至少提供三个可执行选项，格式：

```text
选项A（推荐）：
- 用户需要：
- Skill执行：
- 交付物：
- 推荐原因：
- 直接回复指令：

选项B：
- 用户需要：
- Skill执行：
- 交付物：
- 适用情况：
- 直接回复指令：

选项C：
- 用户需要：
- Skill执行：
- 交付物：
- 适用情况：
- 直接回复指令：
```

选项必须符合当前进度。优先从以下类型组合出三到五项：

- 沿关键路径继续下一生产阶段。
- 修复当前阻塞或返工项。
- 回查上游逻辑和资产，降低后续返工风险。
- 并行准备不会受当前阻塞影响的资产。
- 以保守假设继续，并明确假设和可回滚范围。

不要提供只有措辞不同的重复选项。推荐项应能解除最大阻塞或完成最近里程碑。
用户选定后，直接利用现有上下文执行对应路径；不要再次索要已经提供过的材料。

## 输出格式

简单问题直接给修好后的成品。复杂项目使用：

```markdown
## 当前判断
- 项目阶段：
- 核心卡点：
- 根因：
- 波及范围：

## 进度盘点
- 已完成：
- 进行中：
- 未完成：
- 需返工：
- 阻塞／待确认：
- 下一里程碑及完成标准：

## 已执行的解决方案
- ...

## 交付物
- 完整修订内容或文件

## 自检结果
- 剧情与对白：
- 时长与分镜：
- 资产与连续性：
- 平台可执行性：

## 当前进度
- 当前阶段：
- 完成度依据：

## 下一步选择
- 选项A（推荐）：
- 选项B：
- 选项C：
```

用户只要文件或提示词时压缩进度说明，但仍至少提供三个短选项，除非用户明确要求省略项目指导。
